# Codex 作为 AI 资讯 Agent Harness 的评估

## 结论

可以用，而且适合先做本地 MVP。推荐方式是把 Codex 当作模型与工具的执行内核，在外面包一层自己的业务流水线。不要 Fork Codex 核心仓库，再把采集、数据库和内容业务硬塞进去。

如果只评估今晚这类本地内容 Agent，适配度可以给到 8 分。若把它当成完整的生产级内容中台，适配度只有 6 分，因为调度、数据库、正式采集器、来源授权、告警和编辑审批都需要项目自己建设。

## 为什么可用

Codex CLI 可以非交互运行任务，接收 Prompt，限制沙箱权限，以 JSON Schema 约束最终输出，并把事件流保留下来。本项目已经用这些能力跑完研究、公众号写作和产品经理平台写作三个独立 Turn。

官方还提供 Codex SDK，适合后续由 Node.js 服务编排任务。需要实时展示进度、审批和工具调用时，可以评估 App Server。

- [用户提供的 Codex 开源仓库](https://github.com/openai/codex)
- [Codex SDK 官方文档](https://developers.openai.com/codex/codex-sdk)
- [Codex 非交互模式官方文档](https://developers.openai.com/codex/non-interactive-mode)
- [Codex App Server 官方文档](https://developers.openai.com/codex/app-server)

## 正确的职责拆分

| 组件 | 应承担的工作 | 不应承担的工作 |
|---|---|---|
| Codex Harness | 研究、证据归纳、选题、平台写作、Skill 调用、结构化输出、事件记录 | 长期业务数据库、定时器、平台账号托管 |
| Python 业务层 | 输入校验、URL 规范化、去重、数量限制、阶段状态、QA、文件渲染 | 开放式研究判断和平台长文创作 |
| 采集层 | RSS、API、网页提取、缓存、来源快照、授权和频率控制 | 把聚合页摘要直接当作事实 |
| 数据与调度层 | 每日计划、任务队列、重试、数据库、告警、成本预算 | 用 Codex Thread 充当数据库 |
| 编辑审核层 | 补证、删改、AI 标识、版权、原创声明、最终签发 | 一键批准模型原稿后无人值守发布 |

## 今晚已经证明的部分

- 12 条人工策展候选完成标准化与去重。
- Codex 研究 Turn 选出 10 条资讯，并生成 Claim 级证据包。
- 两个平台使用独立写作 Turn，终稿相似度约 5%。
- Human Writing 检查未发现翻案句、模型腔、黑话等硬问题。
- 终稿 QA 为 0 个错误、0 个警告。
- 生成 5 张统一视觉体系的原创配图。
- 全程没有登录微信公众号或人人都是产品经理，也没有连接草稿箱。

## 今晚还没有证明的部分

- AIHOT、Notion 日报和洞见研报目前用于人工发现线索，尚未形成稳定自动采集器。
- 没有常驻每日调度、任务队列和失败告警。
- 没有数据库、来源正文快照和历史选题查重。
- Codex 阶段失败后目前不会自动限次重试，也不会复用未变化的成功阶段。
- 5 张配图已交付，但图片生成还没有进入主流水线的自动编排。
- 文章是分发前终稿，尚未由发布责任人完成最终事实、版权和平台规则签发。

## 推荐落地路径

第一阶段保留当前结构，先连续手动运行 7 到 14 天，记录候选数量、失败来源、编辑修改幅度、终审耗时和稿件采用率。此时不要改 Codex 核心。

第二阶段补 RSS 与官方 API 采集器，把 AIHOT、Notion 和研报站限定为发现层，关键事实始终回到一手来源。随后加入 SQLite 或 PostgreSQL、定时调度、限次重试、缓存和告警。

第三阶段再建设内部审核台，通过 Codex SDK 或 App Server 展示任务进度、证据、差异和审批。平台连接器即使以后加入，也应停在草稿或待发布状态，保留真人签发。

## 给产品经理的一句话

Codex 很适合做这台机器的发动机，但它不是整辆车。你的资讯 Agent 还需要采集层、业务状态、质量闸门和编辑责任链。今晚的实现已经把发动机装上并跑通了一圈，接下来该补的是稳定采集与长期运行能力。
