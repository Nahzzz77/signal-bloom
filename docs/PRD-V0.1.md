### 0.1 一句话定义

SignalBloom 是一条从“候选信息”到“可审核编辑底稿”的本地内容生产流水线。V0.1 接收人工策展后的每日候选，完成标准化、去重、筛选、证据核验、资讯汇总、平台选题和底稿生成，最后把所有结果放进一个可检查的交付目录，由真人编辑完成实质性改写并决定是否发布。正式自动采集器属于 V0.2。

### 0.2 为什么第一版不直接自动发布

“内容生成自动化”和“账号发布自动化”是两类风险完全不同的能力。前者失败，通常只是稿件需要重做；后者失败，可能导致错误信息公开、版权纠纷、账号处罚或错误声明原创。因此 V0.1 把系统边界固定在分发前，所有文章必须经过人类终审，系统不会持有平台账号、Cookie 或发布 Token。

### 0.3 代码与用户数据边界

公开仓库只保存功能代码、Schema、Prompt、安全配置、虚构结构示例和已授权的 UI 素材。用户的候选线索、规则快照、证据包、稿件、配图、日志和审核包只保存在当前用户的本地目录，不作为开源示例进入 Git。

## 1. 背景与问题

AI 资讯变化快，来源分散。同一件事会被多个媒体重复报道，也会出现发布日期、产品能力、价格、测试结论互相矛盾的情况。人工完成一份日报，通常要反复经历以下工作：

1. 打开许多官网、博客、媒体或社交页面寻找候选资讯。
2. 判断哪些内容真的发生在今天或最近 48 小时。
3. 删除重复消息，把多个来源合并为同一个事件。
4. 区分官方事实、媒体转述、作者判断和未经证实的说法。
5. 从十几条资讯中挑出值得中文读者关注的内容。
6. 为公众号和“人人都是产品经理”分别找角度、写文章、补来源并检查风险。

这里最费时间的并不是“让模型写一篇文章”，而是让文章前面的资料链条可靠、可追溯。若直接把若干网页扔给模型写稿，常见问题是重复、过时、编造事实、混淆来源，以及两个平台只换标题不换内容。

本项目用 Codex 作为 Agent Harness，让模型可以在受约束的执行环境中完成研究、汇总、选题和写作；同时用 Python 业务层管理确定性的校验、状态、文件、覆盖保护和质检。Codex 的会话记录是执行历史，不代替产品自己的业务数据。

## 2. 用户与使用场景

### 2.1 核心用户

**AI 产品经理兼内容负责人**

- 每天需要快速了解 AI 产品、模型、工具、产业和应用变化。
- 希望把资讯变成自己的产品判断，而不是简单搬运新闻。
- 需要向公众号和“人人都是产品经理”准备不同文章。
- 能做最终选题和事实判断，但不希望每天重复做机械搜集、整理和排版。

### 2.2 次要用户

**内容编辑或事实审核者**

- 查看每条结论来自哪里。
- 发现证据不足、表述夸大、平台不适配或版权风险。
- 对文章做最终修改并决定是否进入平台后台。

### 2.3 典型场景

- 晚上手动启动任务，第二天早上打开一个本地审核页验收。
- 临时看到重要资讯，将链接放进种子资料后重新运行。
- 某一来源无法访问时，仍然得到其余来源的部分结果和明确错误记录。
- 对某天结果重新运行时，系统默认拒绝覆盖已有结果；用户显式传入 `--force` 后，才替换这一天的已知产物。

## 3. 产品目标与非目标

### 3.1 V0.1 目标

1. 用户通过一条命令启动当天任务，无需逐阶段手工操作。
2. 系统可接受白名单来源和人工种子资料，形成标准化候选资讯池。
3. 系统完成 URL 规范化、去重、排序和 Top-K 选择。
4. 每条入选资讯都保留来源链接；关键事实被拆成 Claim，并标记证据状态。
5. 自动生成一份 AI 资讯总览。
6. 基于同一份证据包，为公众号和“人人都是产品经理”独立选题、独立生成编辑底稿。
7. 两篇文章都通过 Human Writing Skill 完成写作约束，不编造亲历、测试、数字、引语或平台规则。
8. 自动生成质检报告、执行清单和本地审核页。
9. 所有运行阶段可追踪、失败可定位；默认覆盖保护避免误删当天结果，完整的阶段复用放到 V0.2。
10. 自动化明确停止在发布之前。

### 3.2 V0.1 非目标

- 不建设可供多人登录的 Web 编辑后台。
- 不连接公众号或“人人都是产品经理”账号，不自动发布。
- 不保证抓取整个互联网，也不绕过登录、付费墙、验证码或反爬限制。
- 不把社交媒体传言当作已经证实的事实。
- 不训练专用模型，不做向量数据库和复杂多 Agent 集群。
- 不把图片生成、封面排版、视频、口播和评论区运营纳入自动主流水线。用户已准备的本地配图可进入预览包。
- 不承诺平台审核通过率；平台规则和审核结果由平台决定。
- 不将 Codex Thread 当作长期资讯数据库。
- 不在 V0.1 实现生产级定时调度、短信告警、云部署和自动恢复服务。

### 3.3 平台合规决定的产品边界

截至 2026-08-28，微信公众平台运营规范已明确限制“非真人自动化创作行为”和高频套路化、模板化内容。V0.1 因而不能把“模型生成完整文章”定义为可无人值守发布的成品，也不能用脚本批量连续发布。系统交付的是证据包、选题任务书和编辑底稿，真人编辑必须完成实质性取舍、改写、AI 内容标识复核与最终签发，并保留编辑痕迹。官方规则入口为 `https://mp.weixin.qq.com/mp/opshowpage?action=newoplaw#t3-3-27`。

这一边界不影响今晚验证从信息发现到平台底稿的技术链路，但会改变生产指标。系统不能以“无人参与率”作为核心成功指标，应考察资料覆盖、证据准确率、编辑节省时间、人工修改幅度和发布后纠错率。

### 3.4 来源分层与用户指定来源

用户指定的 AIHOT、Gorden Sun Notion AI 资讯日报和洞见研报 AIGC 搜索全部进入候选池，但用途不同。

| 来源 | 层级 | 系统用途 | 能否单独支撑关键事实 |
|---|---:|---|---|
| AIHOT | Tier 3 | 发现当天热点和聚合外链 | 不能，必须回溯原始出处 |
| Gorden Sun Notion | Tier 3 | 人工策展线索和中文语境 | 不能，优先使用条目内官方链接 |
| 洞见研报 | Tier 3 | 报告标题、机构、日期和公开摘要等背景线索 | 不能，不绕过登录或付费限制，不搬运正文 |
| 厂商公告、论文、代码仓库、监管原文 | Tier 1 | 证明发布日期、能力、范围、价格和政策要求 | 可以，但公司自述仍需注明边界 |
| 可信媒体或专业作者分析 | Tier 2 | 交叉核验和补充外部影响 | 视事实类型而定 |

AIHOT 的公开 Agent 接入页允许个人非商业、公益非商业和组织内部使用，但明确要求对外商业产品、客户交付、公开镜像或批量再分发先取得书面授权。V0.1 只把它用作内部线索发现，并回到原始来源核验，不保存或对外再分发 AIHOT 正文。正式商业化前仍需重新核对 [AIHOT 接入与使用规则](https://aihot.virxact.com/agent) 并取得所需授权。

## 4. 产品原则

1. **先证据，后写作。** 没有证据包就不能进入正式写作阶段。
2. **确定性工作由代码完成。** 文件校验、URL 规范化、去重、状态和硬规则不交给模型自由发挥。
3. **模型判断必须留下结果。** 筛选原因、风险提示、Claim 状态和来源链接都要成为可检查数据。
4. **同一事实源，多种平台表达。** 两个平台共享证据，不共享成稿。
5. **失败要可见。** 宁可交付一份标明“不足”的短稿，也不能用想象补齐。
6. **发布权属于人。** Agent 负责准备材料，人对外部发布承担最终责任。

## 5. 用户旅程

### 5.1 明早验收旅程

1. 用户进入项目目录，确认 Python 和 Codex 登录状态。
2. 用户执行 `./scripts/run_today.sh`；也可以指定日期和种子资料运行。
3. 系统建立 `outputs/<日期>/`，记录本次运行配置和输入哈希。
4. 系统读取白名单来源配置与人工种子资料，形成候选资讯。
5. 系统标准化字段、删除重复项并筛选重要资讯。
6. Codex 研究并生成结构化证据包、总览和平台选题。
7. Codex 分别调用 Human Writing Skill 生成公众号稿和“人人都是产品经理”稿。
8. Python 业务层检查必需文件、来源覆盖、结构和禁用风险，生成质检报告。
9. 系统生成 `review.html`，用户在浏览器中查看资讯、选题、终稿、来源和 QA 风险；阶段状态单独在 `manifest.json` 查看。
10. 用户给出“通过、需修改或不发布”的人工结论。V0.1 不会继续操作外部平台。

### 5.2 日常使用旅程

```text
配置来源或补充链接
        ↓
启动当日运行
        ↓
采集、标准化、去重、筛选
        ↓
研究、事实拆解、证据分级
        ↓
资讯总览与平台选题
        ↓
两个平台独立写作
        ↓
自动质检与本地审核页
        ↓
人工终审
        ↓
人工复制到平台或退回修改
```

## 7. 执行单元与 I/O 契约

一个执行单元是流水线中可以单独记录开始、成功、失败和输入哈希的一步。每一步只接收明确输入，输出固定文件或结构化对象。

| 单元 | 执行者 | 主要输入 | 主要输出 | 失败处理 |
|---|---|---|---|---|
| U00 初始化 | Python | 日期、Provider、配置、种子路径 | RunContext、输出目录、初始 Manifest | 配置无效则立即终止 |
| U10 采集 | Python 种子导入器 | 来源配置、人工策展种子、时间窗 | RawDocument / CandidateItem 列表 | 种子无有效条目则在模型调用前失败 |
| U20 标准化去重 | Python | CandidateItem 列表 | `normalized_items.json` | 数据结构不合法则阻塞研究 |
| U30 研究与筛选 | Codex | 标准化资讯、研究 Prompt、Schema | `research_bundle.json`、事件 JSONL | 本次调用失败则记录并结束；自动重试进入 V0.2 |
| U40 日报渲染 | Python | ResearchBundle | `daily_digest.md` | 缺关键字段则阻塞 |
| U50 公众号写作 | Codex + Human Writing | ResearchBundle、公众号选题、平台规则 | 公众号 ArticleResult JSON / Markdown、事件 JSONL | 证据不足时记录 `blocked`，其他失败单独记录，不影响另一平台 |
| U60 产品经理平台写作 | Codex + Human Writing | ResearchBundle、对应选题、平台规则 | Woshipm ArticleResult JSON / Markdown、事件 JSONL | 证据不足时记录 `blocked`，其他失败单独记录，不影响另一平台 |
| U70 质量检查 | Python | 所有已有交付物 | `qa_report.json` | 输出阻塞项，不掩盖失败 |
| U80 审核包渲染 | Python + React/Vite | Manifest、日报、文章、配图、QA | `review.html`、`assets/`、`articles/` | React 构建失败时保留 `review-legacy.html` 供排错 |

### 7.1 Codex Harness 的职责

- 管理研究和写作 Turn。
- 让模型使用受控工具与 Skill。
- 输出 JSONL 事件，保留可观察执行过程。
- 按 JSON Schema 约束最终结构化输出。
- 使用沙箱和审批边界限制外部影响。

### 7.2 Python 业务层的职责

- 校验输入、配置和 JSON。
- 做 URL 规范化、确定性去重、排序限制和文件渲染。
- 维护阶段状态、输入哈希、错误和重跑规则。
- 执行硬规则质检并生成审核页。
- 确保任何模型输出都不能直接触发外部发布。

## 9. 状态机

### 9.1 整体运行状态

```text
CREATED
   ↓
RUNNING
   ├── 任一关键阶段不可恢复失败 → FAILED
   ├── 有结果但存在阻塞项       → REVIEW_BLOCKED
   └── 所有 P0 交付物完成       → REVIEW_READY
                                      ↓
                         人工决定 APPROVED / CHANGES_REQUESTED / REJECTED
```

V0.1 自动化实际结束于 `REVIEW_READY` 或 `REVIEW_BLOCKED`。后三个人工结论不是自动执行状态，也不能触发外部发布。

### 9.2 单阶段状态

每个 StageRun 使用以下状态：

- `PENDING`：尚未开始。
- `RUNNING`：正在执行。
- `SUCCEEDED`：已成功产生并校验输出。
- `FAILED`：执行失败且当前无可用输出。
- `BLOCKED`：上游输入或事实证据不足，主动停止。
- `SKIPPED`：同输入已有成功结果，或上游失败导致本阶段不应执行。

状态必须进入 Manifest，不能只写在终端滚动日志里。

### 9.3 关键依赖

- U30 依赖 U20 成功。
- U40、U50、U60 都依赖 U30 生成合法 ResearchBundle。
- U50 与 U60 逻辑上可以独立执行和失败。
- U70 应检查已有结果，即使某一篇文章失败也要输出报告。
- U80 尽量总是执行，让用户在审核页看见失败，而不是只得到一个终端报错。

## 10. 人工审核点

### 审核点 A：资讯与证据

检查内容：

- 入选事件是否真的重要，是否发生在时间窗内。
- 来源是否可信，是否误把媒体评论当成官方结论。
- `partial`、`conflicting`、`unverified` 是否被如实标出。
- 是否遗漏用户明确补充的重要链接。

处理结果：保留、删除、降级表述或补充来源。

### 审核点 B：平台选题

检查内容：

- 公众号角度是否值得读者点开，而不是机械日报复述。
- 产品经理平台文章是否落到真实决策、成本、风险、指标或流程。
- 两个平台是否提供不同的读者价值。
- 当前投稿规则和同题库存是否已经人工复核。

处理结果：接受选题、改角度或放弃当天长文。

### 审核点 C：终稿与发布决定

检查内容：

- 标题和正文是否夸大。
- 所有关键数字、日期、引语和能力描述是否能回到来源。
- 是否虚构作者亲历或测试。
- AI 生成合成内容标识、原创声明、引用和跨平台版权安排是否符合当天平台规则。
- 是否存在不适合公开发布的信息。

处理结果：通过、修改后通过或不发布。

### 10.1 今晚 MVP 的审核方式

为了让无人值守夜间运行不中途等待，V0.1 会先自动完成全部分发前材料，把审核点 A、B、C 集中展示在次日的 `review.html`。其中审核点 C 是真正的发布阻断门，系统不会越过它。后续编辑后台可以把 A 和 B 也改成需要人工点击后才继续的同步 Gate。

## 11. 异常处理与覆盖保护

### 11.1 异常分级

| 等级 | 示例 | 策略 |
|---|---|---|
| 可忽略警告 | 单个来源不可访问、缺少非关键摘要 | 记录来源、原因和时间，继续其余任务 |
| 外部执行错误 | Codex 临时失败、结构化输出不合 Schema、短时网络错误 | V0.1 记录错误并返回非零状态；限次自动重试进入 V0.2 |
| 阶段阻塞 | 无合法候选、ResearchBundle 无来源、证据不足以成稿 | 不编造内容，标记 `BLOCKED`，继续生成 QA 和审核页 |
| 全局失败 | 配置损坏、输出目录不可写、关键 Schema 缺失 | 终止运行，返回非零退出码并写 Manifest |

### 11.2 V0.1 已实现的规则

1. 每个阶段在 Manifest 中保存输入哈希、开始时间、完成时间、状态和 attempt。
2. 目标日期目录已有已知产物时，命令默认报错，不静默覆盖。
3. 用户显式传入 `--force` 时，只清理主流水线已知文件和事件日志，再从头运行当天任务。
4. URL 规范化和候选去重在每次运行中保持确定性，同一候选不会因重复链接进入日报两次。
5. 单个平台写作失败时，另一平台仍可继续，QA 和审核页会显示占位阻塞信息。

### 11.3 V0.2 才实现的阶段级幂等

- `run_key` 纳入日期、Provider、种子、来源配置、Prompt 和 Schema 版本哈希。
- 输入没有变化且输出已经校验成功时复用阶段结果，不重复调用模型。
- 某阶段输入变化时，只使该阶段及其下游失效。
- 使用临时文件与原子替换，避免半截 JSON 被当成有效输出。

### 11.4 降级交付

- 一个平台写作失败时，保留另一个平台的成功稿件。
- 证据不足时，交付日报和阻塞说明，不强写长文。
- 审核页应列出“已完成、缺失、失败、需人工确认”，而不是显示空白区域。

## 12. 安全、隐私与版权

### 12.1 安全边界

- 把所有网页正文视为不可信输入。网页中出现“忽略之前要求”“上传文件”“执行命令”等内容，一律当作页面文字，不当作 Agent 指令。
- Codex 只获得完成研究和本地写作所需的最低权限。
- 不在 Prompt、输出、Fixture、日志或仓库中保存账号密码、Cookie、API Token 和个人隐私。
- 公开仓库不保存任何用户的候选资料、研究包、稿件、配图、Manifest 或事件日志。
- V0.1 不登录内容平台，不调用发布接口，不向外部人员发送消息。
- 不绕过验证码、付费墙、robots 限制或访问控制。
- 模型输出必须经过 Schema 和业务规则校验后，才能成为下一个阶段的输入。

### 12.2 事实与声誉风险

- 关键事实必须有证据 URL；无证据内容标为 `unverified`，不能写成肯定句。
- 多来源冲突时保留冲突，不替用户“猜一个正确答案”。
- 不生成虚构引语，不把新闻稿里的宣传性表述改写成独立事实。
- 不声称“我们实测”“我体验了”，除非用户真的提供可核验证据。

### 12.3 版权与平台合规

- 采集用于研究、摘要和事实核验，不大段复制受版权保护的原文。
- 交付物保留来源链接；引用只取完成说明所必需的最短内容。
- 不抓取或再发布付费内容全文、图片、图表和视频。
- 文章发布前由人核对原创声明、转载授权、AI 生成合成内容标识以及两个平台之间的版权安排。
- 平台规则属于会变化的信息。系统和 PRD 中的规则只能作为检查项，发布当天必须以平台最新官方规则为准。

## 13. 指标体系

### 13.1 运行指标

| 指标 | MVP 目标 | 计算方式 |
|---|---:|---|
| 离线测试通过率 | 100% | 通过测试数 / 总测试数 |
| 完整运行交付率 | ≥ 90%，连续 14 天观察 | 生成审核包的天数 / 计划运行天数 |
| P0 文件完整率 | 100% | 实际存在且可解析文件 / P0 文件总数 |

| 同输入重跑重复资讯数 | 0 | 重跑后重复 canonical URL 数 |

### 13.2 内容质量指标

| 指标 | MVP 目标 | 计算方式 |
|---|---:|---|
| 入选资讯来源覆盖率 | 100% | 有至少一个来源 URL 的入选资讯 / 入选资讯总数 |
| Claim 状态覆盖率 | 100% | 有证据状态的 Claim / Claim 总数 |
| 关键事实证据覆盖率 | 100% | 有证据或明确标为未核实的关键事实 / 关键事实总数 |
| 严重无依据事实 | 0 | 人工审核发现的重大编造数量 |
| 跨平台差异合格率 | ≥ 90% | 人工判断角度和结构明显不同的双稿天数 / 双稿天数 |
| 人工采用率 | 先建立基线 | 最终进入修改或发布流程的稿件 / 生成稿件 |

### 13.3 效率指标

| 指标 | 稳定期目标 |
|---|---:|
| 每日人工终审时长 | ≤ 20 分钟 |
| 从启动到审核包完成 | ≤ 60 分钟，具体受来源和 Codex 响应影响 |
| 需要人工补证的入选事件 | 逐周下降 |

MVP 前两周的重点不是追求阅读量，而是先确认系统能稳定交付、事实可追溯，并且真的减少人工机械劳动。

## 15. 验收标准

### 15.1 验收前提

- 本机 Python 版本不低于 3.9。
- 真实运行前已安装并登录 Codex CLI。
- 在克隆后的仓库根目录执行命令。

### 15.2 A 组：离线可运行性，必须全部通过

1. 执行：

   ```bash
   PYTHONPATH=src python3 -m unittest discover -s tests -v
   ```

   预期：测试全部通过，退出码为 0。

2. 执行：

   ```bash
   PYTHONPATH=src python3 -m ai_news_agent run \
     --date 2099-01-01 \
     --seed data/seeds/example.json \
     --provider demo \
     --output /tmp/signal-bloom-demo
   ```

   预期：不调用模型和互联网也能成功生成一套可打开的演示审核包。

### 15.3 B 组：真实 Codex 流水线，核心验收

执行：

```bash
./scripts/run_today.sh
```

或：

```bash
PYTHONPATH=src python3 -m ai_news_agent run \
  --date YYYY-MM-DD \
  --seed data/seeds/YYYY-MM-DD.json \
  --platform-rules data/platform_rules/YYYY-MM-DD.json \
  --provider codex
```

满足以下条件视为流水线通过：

- 命令有明确退出结果，不无限挂起。
- `outputs/YYYY-MM-DD/` 存在。
- 下列文件存在且非空：`manifest.json`、`normalized_items.json`、`research_bundle.json`、`daily_digest.md`、`wechat_article.md`、`woshipm_article.md`、`qa_report.json`、`review.html`。
- JSON 文件可以被标准 JSON 解析器读取；结构化模型输出符合对应 Schema。
- Manifest 能看见每个阶段状态、输入哈希、时间或 attempt，以及失败原因。
- `events/` 中能找到 Codex 研究和写作阶段的事件记录。
- 同一条命令再次运行会触发覆盖保护；只有显式使用 `--force` 才会替换已知产物。

### 15.4 C 组：内容质量，人工抽查

启动本地审核服务：

```bash
./scripts/serve_review.sh YYYY-MM-DD
```

打开：

```text
http://127.0.0.1:4173/review.html
```

逐项确认：

- 日报中的每条入选资讯至少有一个来源 URL。
- 每个 Claim 都有证据状态；无证据内容没有被冒充成已证实事实。
- 日报能回答“发生了什么、为什么重要、风险在哪里”。
- 公众号稿与产品经理平台稿都来自当日 ResearchBundle，而不是自由发挥。
- 公众号稿侧重把变化讲清楚；产品经理平台稿落到决策、成本、风险、指标或团队落地。
- 两篇文章不只是换标题和同义改写。
- 两篇正文均不少于 6000 个汉字，且不含 Markdown 表格。
- 4 至 5 张配图已在网页中进入对应文章段落。
- 文章没有虚构作者亲历、测试、数字、日期或引语。
- 文章保留来源列表、AI 披露提示和编辑备注。
- QA 报告中的阻塞问题被醒目标出；有阻塞项时系统没有声称“可直接发布”。

### 15.5 通过定义

- **技术通过**：A 组全部通过，B 组可完成或能输出可定位的真实外部依赖错误。
- **MVP 通过**：技术通过，并且 B 组生成完整审核包，C 组没有严重无依据事实。
- **内容可发布**：不等同于 MVP 通过，必须由用户完成人工审核点 C 后单独决定。

## 17. 产品决策记录

1. **采用 Codex，但不 Fork Codex 核心。** 本项目通过 CLI / SDK 使用 Harness，业务代码留在独立仓库，降低追随上游源码的维护成本。
2. **V0.1 使用本地文件，不上数据库。** 目的是今晚可运行、明早可看；文件结构同时为后续数据库对象提供原型。
3. **Demo 与 Codex 双 Provider。** Demo 证明工程链路稳定，Codex 证明真实 Agent 能力；二者分开，才能区分“代码坏了”和“外部模型/网络暂时失败”。
4. **Human Writing 只进入写作阶段。** 采集、去重和事实核验不由写作 Skill 代替。
5. **先交付审核包，不自动发布。** 这是 V0.1 最重要的安全边界，也是后续扩平台时仍应保留的产品原则。
